What it is

A pipeline that reads a Hebrew public-tender PDF and pulls out seven specified fields — who published it, what it is called, the qualifying conditions, the contract length, how bids are scored, the bid guarantee, and one field that deliberately is not in the document. For each field it returns the value, an explanation, the source pages, and a 1–5 certainty score.

The point is how it reads. The obvious approach — send all 81 pages to a model, once per field — costs about 81,000 tokens every time and buries the answer in noise. Instead the document is split into pages, every page is tagged once against all seven parameters, and each parameter is then routed to the two or three pages that can actually answer it. It is the same instinct as RAG, but the matching is structural and computed at runtime — there is no vector database and no embedding anywhere in the codebase.

◉ say this out loud — the full answer, ~60 seconds

So the problem is finding specific facts inside a tender that runs to eighty-odd pages. You could just throw the whole document at an LLM for each field, but that's expensive and the accuracy drops, because the answer is competing with three hundred pages of noise.

What I built instead splits the PDF into pages and tags each page once — for every parameter, how relevant is this page, zero to three, plus a short quote as evidence. That's one cheap model call per page. Then routing is just ranking and capping: each parameter goes to its top few pages, and only those get sent to the extractor.

It's RAG-shaped, but there's no vector store. The unit is a page, not a chunk, because a tender is authored in pages — clause headings and appendix boundaries line up with them, and "see page 47" is a citation a human can actually check.

Then two things verify the answer. A second model from a different family re-reads the exact same pages completely blind — it is never shown the first answer — and plain code compares the two readings. And separately, a string check confirms the quote it cited really appears on the page it cited — no model involved in that one, which is exactly why I trust it.

Measured end to end it's 62% fewer tokens than the naive baseline, and it got all seven fields right on the dev tender and held up on a completely different one I never tuned against.

▸ the 15-second version — when they only want the headline

It extracts seven fields from long Hebrew tender documents. Rather than sending the whole PDF to a model for each field, it tags every page once, routes each field to the two or three pages that can answer it, and verifies the result with a second model plus a deterministic check that the quoted text is really on the page it claims. 62% fewer tokens, and every answer is traceable to a page number.

The follow-up they will actually ask. "Isn't tagging every page just as expensive as reading the document once?" Yes — nearly. Tagging costs 190,328 tokens, roughly 2.3× a single read, because each page prompt carries the system prompt and the parameter catalogue. The win is not on the first parameter, it is amortisation: tagging is paid once and reused by all seven, while the baseline pays for a whole document every single time. Break-even is 2.4 parameters. Say the number before they find it.

A scene

A city water utility publishes a tender: it wants a company to look after its databases. The document is 81 pages of legal Hebrew. Someone at a bidding company has to find six or seven specific facts in it — how long is the contract, how big a bank guarantee do we have to put up, what are the minimum qualifications, how will they score us. Doing that by hand takes hours. Do it for forty tenders a month and it is somebody's whole job.

This program does that reading. You give it the PDF and a list of the facts you want, and it gives you back each fact, where in the document it found it, and how sure it is.

How it works, in four steps

One — cut it up. The PDF becomes a list of pages. Page 1, page 2, and so on. Each page is treated as its own little document.

Two — label every page. An AI model reads each page once and answers, for every fact on the list: is the answer here? It scores 0 to 3 and copies a short quote as proof. This happens once per page, no matter how many facts you are looking for.

Three — pick the pages. Now for each fact you just look at the scores and take the best two or three pages. No AI needed — it is sorting a list.

Four — read only those pages. A stronger model gets those few pages and pulls out the actual answer. Then a second, different model reads the same pages on its own — without ever seeing the first answer — and plain code compares the two readings. And a plain piece of code checks that the quote really does appear on the page.

Why not just send the whole PDF?

It costs a lot and the answer gets lost. A model reading three sentences finds the guarantee amount more reliably than one reading eighty pages.

Why pages and not paragraphs?

Because a page number is something a human can check. "It is on page 7" can be verified in five seconds. "It is in chunk 213" cannot.

What is a token?

Roughly a piece of a word. AI models are billed per token, so "fewer tokens" means "cheaper". The whole cost argument is counted in tokens.

Why two models?

One model checking its own work agrees with itself. A different model has different blind spots, so when the two disagree that is a real signal something is off.

What is the fake field for?

One of the seven fields is not in the document on purpose. If the program invents an answer for it, the program is broken. It is a trap, and passing it matters.

What does "grounded" mean?

The model quotes a sentence as proof. Grounded means ordinary code went and checked that the sentence is genuinely on that page. No AI in that check, which is why it can be trusted.

◉ five sentences worth memorising

1. It reads long Hebrew tender documents and pulls out specific facts.

2. Every page gets labelled once, then each fact is routed to its best two or three pages.

3. That is 62% cheaper than sending the whole document for every fact.

4. A second, different model reads the same pages blind, and code compares the two readings.

5. One field is a deliberate trap that must come back "not found" — and it does, on both documents.

def detect_rtl_reversal(text: str) -> bool:
    """Is this extracted Hebrew stored back-to-front?

    Some PDF producers emit Hebrew in visual rather than logical order, and PyMuPDF
    faithfully returns what is stored — so "כללי" comes back as "יללכ". Rather than
    flip everything blindly (which would corrupt a correctly-encoded document), use an
    orthographic invariant: the five final-form letters ךםןףץ may ONLY end a word.
    If they are turning up at the START of words, the text is reversed.

        if len(word) < 2:
            continue
        starting += word[0] in HEBREW_FINALS
        ending += word[-1] in HEBREW_FINALS
    return starting > ending

2 · The repeated header is metadata, not noise
solution.py:547–564 · detect_boilerplate()
The single highest-leverage discovery in the project. Getting this wrong collapsed routing for two of the seven parameters.
def detect_boilerplate(pages: list[Page], threshold: float = 0.5) -> set[str]:
    """Find the header/footer lines that repeat across most pages.

    Tenders stamp every page with the publisher, the tender number and a signature
    block. Left in place this is not merely wasted tokens — the stamp *contains the
    answers* to client_name and tender_name, so those two parameters match on every
    page and routing collapses to "all 81 pages". Removing it is what makes the
    metadata parameters routable at all.
    """
    from collections import Counter

    counts: Counter[str] = Counter()
    for page in pages:
        for line in {ln.strip() for ln in page.raw_text.split("\n") if ln.strip()}:
            counts[line] += 1

    cutoff = len(pages) * threshold
    return {line for line, count in counts.items() if count > cutoff and len(line) > 3}
553–559
The docstring states the failure, which is the real justification. Eight lines repeat on ~80 of 81 pages — 8.7% of every character in the document. They also contain the publisher and the tender name, so before this existed client_name matched 80/81 pages and tender_name 81/81. Routing had nothing to rank.
563–565
A set per page, not a list. A line repeated twice on one page must count once, or a page with a doubled footer would skew the frequency.
568–569
Two conditions. More than half the pages, and longer than three characters — the length guard stops short strings and stray digits being treated as chrome.
—
What is NOT here matters most. These lines are not deleted. build_document_meta() reassembles them into a document-level record, because מי שבע appears nowhere on page 1 — only in the running header from page 2 on. Deleting them would have made client_name unanswerable.
the alternative I didn’t choose

Strip the header and exempt the cover page. That was my first attempt and it was wrong. I checked, and page 1 is a title page that never names the utility — the client name exists only in the running header. Exempting the cover would have preserved nothing. Turning the header into a document-level field is what lets the metadata parameters be answered with one page sent instead of six.

4 · Routing is ranking, not retrieval
solution.py:834–876 · match_parameters_to_pages()
The heart of the thesis. If an interviewer challenges "why not embeddings", this function is the answer.
def match_parameters_to_pages(
    tags: dict[int, PageTags],
    specs: list[ParameterSpec],
    pages: list[Page],
    meta: DocumentMeta,
    threshold: int = RELEVANCE_THRESHOLD,
    candidates: dict[str, set[int]] | None = None,
) -> dict[str, list[int]]:
    """parameter -> [2, 3, 7] — a required output of the assignment, not just a step.

    Two routes, chosen by parameter FAMILY (config-driven, never by parameter name):

    * metadata  — answered from the running header, which is identical on every page.
                  Cites the page it first appears on and sends no body pages at all.
    * everything else — ranked by the tagger's relevance score, nudged by page role,
                  then capped. Sending few pages is a graded objective, so this ranks
                  and caps rather than collecting everything plausible.

    A parameter with no page over the threshold still gets pages (fallback_pages) —
    never an empty set.
    """
    by_number = {p.number: p for p in pages}
    role_bonus = {"body": 0.3, "cover": 0.2, "form": -0.3, "appendix": -0.4, "toc": -1.0}

    page_map: dict[str, list[int]] = {}
    for spec in specs:
        if spec.family == "metadata":
            page_map[spec.name] = [meta.first_page]
            continue

        scored: list[tuple[float, int]] = []
        for number, page_tags in tags.items():
            for rel in page_tags.relevance:
                if rel.parameter != spec.name or rel.score < threshold:
                    continue
                page = by_number[number]
                density = min(len(rel.evidence), 60) / 600      # tie-break on evidence length
                scored.append((rel.score + role_bonus.get(page.page_role, 0.0) + density, number))

        scored.sort(key=lambda item: (-item[0], item[1]))
        chosen = sorted(number for _, number in scored[: spec.max_pages])
        page_map[spec.name] = chosen or fallback_pages(spec, tags, candidates, pages)
    return page_map
842–854
Two routes, chosen by family, never by parameter name. That distinction matters: keying behaviour off client_name would be hardcoding for this document. Family comes from config, so an unseen parameter still routes.
856
The role bonus encodes the appendix trap. A guarantee amount appears in both the binding clause and the blank template in a נספח. Body scores +0.3, appendix −0.4, table of contents −1.0, so the binding clause wins a tie it would otherwise lose.
860–862
The metadata short-circuit. These parameters send the document header plus the page it first appears on — the answer lives in the running header, not in any body clause.
873–875
No vectors, no similarity — and never an empty page set. Ranking is a sort over integers the tagger already produced, capped to a hard budget. When nothing clears the threshold, fallback_pages() (line 801) sends the best sub-threshold pages, then lexical hits, then the opening pages — the spec says every parameter gets a prompt and pages, and an absence concluded from an empty prompt proves nothing.
the alternative I didn’t choose

Embed every page and rank by cosine similarity to the parameter description. That is the standard answer and it would work — but it buys nothing here and costs several things. Hebrew embedding quality is far more variable than Hebrew generation quality; a cosine score is not inspectable, whereas “the tagger scored page 7 a three and quoted this sentence” is; and I would still need an LLM call at extraction anyway. I would reach for embeddings if the parameter list were open-ended and large — at seven fixed fields, tagging once against all seven is both cheaper and auditable.

5 · The model supplies the number; evidence caps it
solution.py:1110–1158 · final_score()
The spec says "ask the model" for the 1–5. This is how you do that without simply trusting it.
def final_score(item: Extraction, judge_score: int, verdict: str) -> int:
    """The model supplies the number; verifiable evidence caps it.

    For a FOUND value the judge's number is the ceiling and the deterministic checks pull
    it down. For a NOT-FOUND value the score is the agreement between the two models, which
    is what the spec asks for: "comparing the results of the two runs, saving a certainty
    score based on the comparison". A confident, agreed absence is a correct answer and
    scores 5.

    Two things still lower it, and both are about not having looked properly rather than
    about disagreement:
      * coverage_complete False -> some pages never tagged, so routing may have missed the
        page that held the answer. No absence claim deserves a high score. -> 3
      * the call failed -> we never got an answer at all. -> 1
    """
    if item.error:
        return UNVERIFIED_SCORE          # we never got an answer — claim nothing

    if verdict == "unverified":
        # The second run's call failed, so there is no second opinion to score. This is
        # NOT low confidence in the value — it is absence of confirmation, and collapsing
        # the two would let a rate limit masquerade as a quality judgment.
        if item.status != "found":
            return 3                      # cannot confirm an absence on one reading
        return 3 if item.grounded else 2  # extracted, quote checks out, but unconfirmed

    if item.status != "found":
        if not item.coverage_complete:
            return 3                      # routing was built on incomplete tags
        if verdict == "disagree":
            return 2                      # the second run DID find something — real conflict
        # Both models read the routed text and agree the value is absent. That
        # agreement is the score, exactly as it is for a found value.
        #
        # max_relevance is NOT allowed to lower this. A high tagger score means the
        # cheapest model, triaging one page in isolation, thought the answer might be
        # there — while two stronger models that actually read the text disagree. The
        # tagger loses that argument. It is recorded as absence_contested in the
        # diagnostics instead of being hidden inside the number.
        return 5

    score = judge_score
    if verdict == "disagree":
        score = min(score, 2)
    elif verdict == "partial":
        score = min(score, 3)
    if not item.grounded:                # the cited quote is not on the cited page
        score = min(score, 3)
    return max(1, min(5, score))
1111–1124
Two scoring regimes, and the docstring says which is which. For a found value the second run’s confidence is a ceiling that deterministic checks pull down. For a not-found value the score IS the agreement between the two runs — exactly what the spec asks for: “comparing the results of the two runs, saving a certainty score based on the comparison”.
1125–1126
A failed extraction claims nothing. The difference between “we looked and it is not there” and “we never got an answer”. Collapsing those two is how a system reports a confident lie.
1128–1134
An unavailable second run is not a bad answer — a found value drops to 3 when its quote verified and 2 when it did not, never to 1. This branch was dead code until an audit caught the caller passing cannot_verify instead of unverified: a quota outage was scoring correct, grounded answers 1/5. One word fixed it.
1132–1149
An agreed absence scores 5, and max_relevance may not lower it. A high tagger score means the cheapest model, triaging one page in isolation, suspected the answer was there — while two stronger models that actually read the text disagree. The tagger loses that argument; the tension is recorded as absence_contested in the diagnostics rather than buried in the number.
1151–1158
For a found value the caps only ever lower. Disagreement, partial agreement, or a quote not verifiably on the cited page each pull it down. Nothing can raise a score above what the blind second run gave.
the alternative I didn’t choose

Just return whatever 1–5 the second model emitted. That is what the spec literally asks for, and it is what most submissions will do. The problem is a model will happily say 5 while citing a quote that is not on the page — I saw exactly that before the grounding check existed. The cost of my version is that the score is no longer a single model’s opinion, so it is harder to explain in one sentence; I think the trade is obviously worth it for a legal document.

6 · A hallucination check with no model in it

def check_grounded(
    quote: str,
    pages: list[Page],
    page_numbers: list[int],
    meta: DocumentMeta | None = None,
    min_overlap: float = 0.8,

    """Does the cited quote actually appear where it says it does?

    Deterministic — no LLM — which is exactly why it can be trusted as a hallucination
    check. Searches raw_text (not body_text) plus the document header, because a quote
    may legitimately come from the running header that body_text has removed.

    Exact substring first; otherwise word overlap, since a model may re-space or clip
    a quote without inventing it.
    """
    if not quote:
        return False

    haystack = normalize_hebrew(" ".join(
        p.raw_text for p in pages if p.number in page_numbers
    ))
    if meta is not None:
        haystack += " " + normalize_hebrew(meta.header_text)
    if not haystack.strip():
        return False

    needle = normalize_hebrew(quote)
    if needle[:40] and needle[:40] in haystack:
        return True

    words = [w for w in needle.split() if len(w) > 1]
    if not words:
        return False
    present = sum(w in haystack for w in words)
    return present / len(words) >= min_overlap

Why it is trustworthy is stated in the docstring. No LLM participates, so it cannot share a failure mode with the extractor or the second run.

the alternative I didn’t choose

Ask a third model “does this quote appear on this page?” It would handle paraphrase better. But it costs a call per parameter, it can be wrong in the same direction as the other two models, and it turns my one model-independent signal into a third model opinion. The honest limitation of my version is that it measures string presence, not semantic support — a quote can be real and still not support the answer. Catching that is what the agreement check is for.

06

Concepts, with pictures

The mechanisms this project depends on, drawn. Each ends with the real failure mode — not the textbook caveat, the thing that breaks here.

1 · Page-level routing instead of vector retrieval

solution.py:834 match_parameters_to_pages()

Standard RAG embeds chunks and ranks them by cosine similarity to the query. This does the same job — narrow the document, then generate — but the narrowing is a lookup over scores an LLM already assigned, page by page. The retrieval unit is a physical page because a tender is authored in pages, and because "page 7" is a citation a human can check in five seconds.

what breaks It breaks when the document has no usable page structure — continuous prose, or a 400-page appendix where one clause spans nine pages. It also assumes the parameter list is small and fixed: tagging against 200 parameters per page would make the prompt enormous, and embeddings would win.

2 · Why tagging every page is still cheaper

solution.py:1464 run_ablation()

The objection lands immediately: tagging all 81 pages costs about as much as reading the document once, so where is the saving? It is real — tagging costs 190,328 tokens, roughly 2.3× a single read, because every page prompt carries the system prompt and the parameter catalogue. The saving is amortisation. That cost is paid once and reused by all seven parameters; the baseline pays for a whole document on every single one.

what breaks It breaks below three parameters — at one or two fields, just send the document. It also breaks if the tag schema has to change per query, because then tagging is no longer a one-off and the fixed cost recurs.

3 · The negative control, and scoring an absence

solution.py:1199 attach_absence_evidence()

One of the seven parameters is deliberately not in the document. If the pipeline invents a value for it, the pipeline is broken — so it is the cheapest honest quality signal available, and it needs no labels. The harder question is what score a correct "not found" deserves. Same answer as for a found value: the agreement between the two runs. If the extractor and the blind second run both read the routed pages and both report the value absent, that is a confident correct answer and scores 5. What lowers it is not having looked properly — pages that failed to tag, or a call that failed outright.

what breaks It breaks when both models miss the same thing. If a value is present but phrased so unusually that routing never surfaces its page, the extractor and the second run will agree it is absent and score it 5 — confidently and wrongly. Agreement between correlated models is the weak point, which is why absence_contested is logged whenever the tagger disagrees with both of them, and why incomplete tag coverage caps an absence at 3.

4 · A hallucination check with no model in it

solution.py:1161 check_grounded()

Every extracted value carries a verbatim Hebrew quote, and ordinary code checks that the quote really appears on the page the model cited. Exact substring first; word overlap at 0.8 as a fallback, because a model may re-space or clip a quote without inventing it — especially in Hebrew, where PDF extraction loses the space between a Hebrew word and a Latin one.

what breaks It measures string presence, not semantic support: a quote can be genuinely on the page and still not justify the answer given. Catching that is the agreement check’s job. It also searches raw_text rather than body_text — searching the stripped text reported client_name as ungrounded when it was perfectly correct.

5 · Logical versus visual order in Hebrew PDFs

solution.py:417 detect_rtl_reversal()

A PDF may store Hebrew in reading order or in left-to-right visual position. PyMuPDF returns whatever is stored, so on some documents every word comes back backwards — which silently destroys keyword matching while looking like a prompt problem. Rather than always reversing (which would corrupt a correct document), the code tests an invariant of the writing system.

what breaks It needs at least a few multi-letter Hebrew words per page to vote, which is why the decision is taken once for the whole document rather than per page. A document mixing both orders — some pages logical, some visual — would defeat the majority vote entirely.

6 · Schema-constrained decoding

solution.py:200 GeminiProvider.complete()

The schema is handed to the API and the decoder is masked so only tokens that can still produce a valid document are sampled. That is why there is no try: json.loads(...) anywhere in this codebase, and no retry-on-malformed path. The same Pydantic model is simultaneously the API contract, the runtime validator and the internal type.

what breaks A constrained decoder will happily fill a required string field with something plausible rather than leaving it empty — which is exactly how a rate-limited call produced a schema-valid empty object that then got cached as truth. Shape validity can disguise semantic emptiness.

7 · A blind second run instead of an answer-reviewing judge

solution.py:1220 verify_and_score() · solution.py:1078 compare_answers()

The first design showed a judge the candidate answer and limited anchoring by schema field order — the judge stated its own reading before being asked whether it agreed. An audit flagged the obvious problem: the candidate was still in the context, so the confidence number partly measured the judge’s willingness to agree. The rebuild removes the judge entirely. A second model receives the identical extraction prompt and the identical pages — and nothing else — then plain code compares the two readings: normalized containment first, then token overlap (≥0.8 agree, ≥0.4 partial, else disagree).

what breaks The comparison is textual: containment and overlap can call a heavy paraphrase “partial” where a human would say “agree”, and both runs are one vendor, so correlated misses still agree confidently. On contract_period the second reading disagreed with the extractor and was closer to the reference answer both times — that is the mechanism catching a real slip, and it survived the redesign.

8 · Bounded concurrency and resumability

solution.py:699 tag_pages()

The work is I/O-bound — 81 network calls — so asyncio with a semaphore is the right shape. The permit count is not a performance tuning knob here so much as a rate-limit one: ten permits produced sustained 429s and lost fifteen pages, five ran clean.

what breaks The semaphore is a fixed constant, not adaptive. A different key with a different quota needs it changed by hand, and there is no token-bucket or adaptive concurrency — under a stricter quota the pipeline just backs off and takes longer.

9 · Content-hash caching and the failure that got memoised

solution.py:349 cache_key()

Page tags are keyed by a hash of the page text, the prompt version and the model, so any change to any of them misses cleanly. That makes the pipeline idempotent and resumable — and it is what makes a live demo possible at all, since a warm run finishes in 0.17 seconds against 265 cold.

what breaks It broke in the worst possible way first: a transient rate limit produced a schema-valid empty object, which was cached and served forever after as a fact about the document. A negative cache with a short TTL would be the scalable fix; not caching failures at all is the simpler one.

Question drill

Questions an interviewer would actually ask about THIS repo.

08

Defense mode

Not the first question — the second one. Where the honest answer is "I didn't handle that", it says so.

▸"You tag every page with an LLM. That is the same cost as reading the whole document — your saving is an illusion."

Partly true, and I should give you the number: tagging is 190,328 tokens, about 2.3 times a single read of the document. So on one parameter you're right, routing loses. The saving is amortisation — that cost is paid once and reused by all seven parameters, while your approach pays for a whole document each time. Break-even is 2.4 parameters, and at seven it's 62% fewer tokens end to end.

If they only ever wanted one or two fields, I'd tell them to skip this and send the document.

▸"Agreement between two models is not accuracy. What does your certainty score actually mean?"

You're right, and I'd separate the two things. Agreement is a consistency proxy — two correlated models can agree and both be wrong, and mine are the same vendor, so it's cross-size not cross-vendor independence. That's why the score isn't only agreement: the deterministic groundedness check shares no failure mode with either model, and it can only cap the score downward, never raise it.

The score is evidence-capped, not calibrated. I have no reliability curve because fourteen data points can't produce an honest one, and I'd rather say that than draw one.

▸"Seven out of seven on one document. That is n=1. Why should I believe any of this generalises?"

I wouldn't ask you to believe it from that. The 7/7 is a checklist on one document, not an accuracy rate, and I say so in the README. What I'd point at instead is the holdout — a different authority, 46 pages, never tuned against, where the scoring weights are reversed and the whole boilerplate mechanism finds nothing yet the metadata still resolves. And the label-free metrics, which run on any document without answers.

Two documents is a very small n and no amount of framing fixes that. What it buys me is evidence I didn't overfit, not evidence of an accuracy rate.

▸"Your judge sees the answer before it judges. That is not independent verification."

It used to — and that was a flagged finding. The first design showed the judge the candidate answer and mitigated anchoring by schema field order. I rebuilt it: the second model now receives the identical extraction prompt and the identical pages, and nothing else — it never sees the first answer. The two readings are compared by plain code (compare_answers): normalized containment, then token overlap.

What's left to attack is the comparison itself — textual overlap can under-call a heavy paraphrase as partial — and that both runs are still one vendor. But anchoring is gone structurally, not mitigated.

▸"You built a provider abstraction, a cache layer, and a diagnostics file for a home assignment. Is that not over-engineering?"

Two of the three earned their place by catching bugs. The cache is what makes the pipeline resumable under rate limits, and I needed that — a cold run takes four minutes and kept dying. The diagnostics file is where I found that window expansion was firing on 52 of 81 pages and nearly doubling what I sent. The provider seam is the weakest of the three at about sixty lines, justified only because moving off the free tier was planned.

If no provider swap were coming I'd have deleted that seam. A seam you never use is just indirection.

▸"Prompt caching is in your plan and not in your code. What else did you write down and not do?"

That's a fair hit and it's the one I'd flag myself. Prompt caching, and the third status value — my docstrings described a found/not-found/ambiguous design and only two states ever existed, so the conflict case I made much of is handled by tagger scoring rather than by a distinct status. I did a cleanup pass over exactly this before we spoke: dead constants, a config field that was loaded and never read, computed features that were being discarded.

The documentation drifted ahead of the code, which is my mistake. PLAN.md now records what was planned and not built, because that's the half people usually delete.

▸"Your gazetteer excludes seven pages out of eighty-one. What is it actually for?"

Honestly, less than I claimed when I designed it. I described it as a meaningful cost cascade and the measurement corrected me — since pages are tagged once for all parameters, excluding seven pages is about an eight percent saving, not the tiering I'd imagined. What it does still buy is a shorter prompt on no-signal pages and a lexical density signal for routing tie-breaks.

I'd keep it, but I'd stop describing it as a cascade. On an 800-page tender with many form pages the ratio would improve; at this size it's marginal and I should say so.

▸"If the model returns a schema-valid but empty object, how would you even know?"

That exact thing happened, and for a while I didn't know — a 429 produced an empty PageTags, it was cached, and the document permanently believed those pages were blank. Schema validity disguised semantic emptiness. The fix was to stop inferring success from shape: call_with_retry returns an explicit ok flag, failures are never cached, and an extraction error is a distinct state from not-found with a loud warning on the run.

I found that by reading diagnostics, not by a test. There's no automated test for it, and if you asked me what to write first, that would be it.

09

Known weaknesses, stated plainly

The things a senior reviewer will find. Owning a gap well is stronger than hiding it badly.

01 No labelled evaluation set, so no precision or recall

Routing quality is never quantified. There's no page-level gold set saying which pages truly contain each parameter, so I report no precision, recall or F1 for the retrieval stage — only pages sent versus pages actually cited, which is a weak proxy.

why it’s that way

It's about two hours of hand-labelling on one document, and I kept prioritising pipeline work over it. The assignment also emphasises structure over accuracy, which made it easy to defer.

say this
“I didn't label a gold set, so I don't quote retrieval metrics — I'd rather report nothing than compute an F1 from model-generated labels and present it as measured. It's the first thing I'd build next, and I know roughly what it costs.”

02 Verification is cross-size, not cross-vendor

The extractor and the verifying second run are both Gemini — 2.5-flash and 3.5-flash-lite. Their errors are less correlated than a same-model self-check, but far more correlated than two genuinely different providers.

why it’s that way

Free-tier development on one provider. An Anthropic provider now ships in the code — the UI has a Gemini/Claude toggle — but each provider’s role pair is still same-vendor (flash/flash-lite, or Opus 5/Sonnet 5). Mixing vendors is a one-line PROVIDER_MODELS edit.

say this
“It's cross-size independence, not cross-vendor, so my agreement numbers are optimistic. The Anthropic provider is already wired in — crossing vendors is a one-line model-map edit, and it's what I'd do before trusting agreement as a quality gate.”

03 Nothing is pinned for reproducibility

Temperature is never set, so the provider default applies. I observed real run-to-run variation — the same page scored 3 for a parameter on one run and 2 on the next.

why it’s that way

I was iterating fast against a rate-limited free tier and never went back to pin it. The result cache masked the problem, because a warm run is deterministic by accident.

say this
“I never pinned temperature, and I saw tag scores move between runs. The cache hides it day to day, but it means my numbers have an unmeasured variance band around them and I can't quote them to three significant figures.”

04 No automated tests

There is no test suite. Correctness was established by running the pipeline and reading the diagnostics, plus a scoring-ladder check I ran once in a throwaway script and didn't keep.

why it’s that way

The assignment asks for a single script and explicitly waives error handling, so tests were out of scope for the deliverable — but that's a reason, not a justification for zero.

say this
“There are no tests, and the two bugs that actually bit me — cached failures and errors reported as not-found — are exactly the kind a test would have caught. final_score is a pure function with four inputs; that's where I'd start, and it's twenty minutes.”

05 The documentation drifted ahead of the code

PLAN.md described prompt caching that was never implemented, and docstrings described a three-state found/not-found/ambiguous design when only two states exist. Several computed fields were being discarded, and a config field was loaded and never read.

why it’s that way

The plan was written before the code and updated less often than the code changed. Classic drift, made worse by building against a moving free-tier quota. The same applies to the measured tables: the 62% ablation and the README results predate the blind-verification and fallback-routing changes — re-run both tenders and --ablation before quoting them.

say this
“My docs got ahead of my code in a few places and I did a cleanup pass over it. PLAN.md now records what I planned and didn't build, including prompt caching, because that's the half people usually quietly delete.”
